## 2. Job Application Flow Diagnosis

### What Works

The backend is **fully functional**:

1. **Prisma schema** — `Job` and `JobApplication` models are properly defined with a one-to-many relation (`Job.applications` → `JobApplication[]`, `JobApplication.job` → `Job`). The cascade delete is set. All relevant fields exist (`fullName`, `email`, `phone`, `education`, `experience`, `coverLetter`, `cvFileName`, `cvUrl`, `status`, `createdAt`).

2. **User submission** — `POST /api/jobs/apply` correctly creates a `JobApplication` record. It validates required fields, saves the uploaded CV to `public/uploads/cvs/`, and stores the `cvUrl`. No bugs here.

3. **Admin API — list applications** — `GET /api/admin/jobs/applications?jobId=<id>` correctly queries `JobApplication` with `include: { job: { select: { title: true } } }`. It returns `{ ok: true, applications: [...] }`.

4. **Admin API — update status** — `PUT /api/admin/jobs/applications?id=<id>` correctly updates `status`.

5. **Admin UI — `JobsTab` component** — The `JobsTab` in `admin-app.tsx` **does exist** and **does render applications**. When the admin clicks a job row, it calls `loadApps(jobId)`, fetches from `/api/admin/jobs/applications?jobId=...`, and renders each applicant's name, email, education, experience, cover letter, and CV download link. It also renders a dropdown to update the applicant status.

### What Is Broken / Missing

**The `useFetch` hook silently returns empty arrays for the jobs list.**

Look at the `useFetch` hook used throughout `admin-app.tsx` (lines 44–56):

```ts
function useFetch<T>(url: string, deps: unknown[] = []) {
  // ...
  const reload = useCallback(async () => {
    // ...
    const r = await fetch(url);
    const j = await r.json();
    setData(j.items ?? j.testimonials ?? []);  // <-- BUG IS HERE
  }, [url]);
  // ...
}
```

The hook always extracts `j.items ?? j.testimonials ?? []`. But `GET /api/admin/jobs/route.ts` returns:

```json
{ "ok": true, "jobs": [...] }
```

The key is `"jobs"`, not `"items"`. So `j.items` is `undefined`, `j.testimonials` is `undefined`, and `setData` receives `[]` — an **empty array every time**. The admin sees "0 postings" even when jobs exist in the database.

This same bug affects every admin tab that uses `useFetch` with an API that returns a non-`items`/non-`testimonials` key:

| Tab | useFetch URL | API response key | Bug? |
|-----|-------------|-----------------|------|
| Saccos | `/api/admin/saccos` | `items` | ✅ Works |
| News | `/api/admin/news` | `items` | ✅ Works |
| Events | `/api/admin/events` | `items` | ✅ Works |
| Testimonials | `/api/admin/testimonials` | `testimonials` | ✅ Works |
| Applications (membership) | `/api/admin/applications` | `items` | ✅ Works |
| Messages | `/api/admin/messages` | `items` | ✅ Works |
| Subscribers | `/api/admin/subscribers` | `items` | ✅ Works |
| Members | `/api/admin/members` | `items` | ✅ Works |
| Menu | `/api/admin/menu` | `items` | ✅ Works |
| Pages | `/api/admin/pages` | `items` | ✅ Works |
| **Jobs** | `/api/admin/jobs` | **`jobs`** | ❌ **BROKEN — only one** |

**Because the jobs list never loads**, the admin never sees any job rows, so they can never click a job to trigger `loadApps()`. The applications are in the database — they just can't be reached through the UI.

### Root Cause

**Two-part cause:**

1. `useFetch` hardcodes `j.items ?? j.testimonials ?? []` but `GET /api/admin/jobs` returns `{ ok, jobs }`.  
   Fix: Either change the API to return `{ ok, items }`, or update `useFetch` to also check `j.jobs`.

2. The cleanest and most maintainable fix is to **change `GET /api/admin/jobs/route.ts`** to return `{ ok: true, items: jobs.map(...) }` instead of `{ ok: true, jobs: ... }`. This aligns it with every other admin API and requires no changes to the shared `useFetch` hook.

## 3. Exact Fixes Needed

### Fix 1 — File: `src/app/api/admin/jobs/route.ts`

**Change:** Rename the response key from `jobs` to `items` in the `GET` handler so it matches what `useFetch` expects.

Also check: the `JobsTab` calls `useFetch("/api/admin/jobs")` and accesses `data` directly as the jobs array. After this fix, `data` will contain the jobs objects. The `JobsTab` component code maps over `jobs || []` via `const { data: jobs, ... } = useFetch(...)` — so renaming also requires updating the `JobsTab`'s `loadApps` data handling. See Fix 2 for the complementary UI fix.

```ts
import { NextResponse } from "next/server";
import { db } from "@/lib/db";
import { verifyAdmin } from "@/lib/auth";

// GET — list all jobs (admin) with application counts
export async function GET() {
  if (!(await verifyAdmin())) return NextResponse.json({ error: "Unauthorized", ok: false }, { status: 401 });
  const jobs = await db.job.findMany({
    orderBy: { createdAt: "desc" },
    include: { applications: { select: { id: true, status: true } } },
  });
  // Return as "items" so the shared useFetch hook picks it up correctly
  return NextResponse.json({
    ok: true,
    items: jobs.map((j) => ({
      ...j,
      applicationCount: j.applications.length,
      applications: undefined,
    })),
  });
}

// POST — create a job posting  (unchanged)
export async function POST(req: Request) {
  if (!(await verifyAdmin())) return NextResponse.json({ error: "Unauthorized", ok: false }, { status: 401 });
  const b = await req.json();
  const job = await db.job.create({
    data: {
      title: String(b.title || ""),
      department: String(b.department || "Operations"),
      type: String(b.type || "Full-time"),
      location: String(b.location || "Addis Ababa"),
      description: String(b.description || ""),
      requirements: b.requirements ? String(b.requirements) : null,
      salary: b.salary ? String(b.salary) : null,
      closingDate: b.closingDate ? new Date(String(b.closingDate)) : null,
      status: String(b.status || "open"),
    },
  });
  return NextResponse.json({ ok: true, id: job.id });
}

// PUT — update a job  (unchanged)
export async function PUT(req: Request) {
  if (!(await verifyAdmin())) return NextResponse.json({ error: "Unauthorized", ok: false }, { status: 401 });
  const url = new URL(req.url);
  const id = url.searchParams.get("id");
  if (!id) return NextResponse.json({ error: "id required", ok: false }, { status: 400 });
  const b = await req.json();
  const data: Record<string, unknown> = {};
  for (const k of ["title", "department", "type", "location", "description", "requirements", "salary", "status"]) {
    if (b[k] !== undefined) data[k] = String(b[k]);
  }
  if (b.closingDate !== undefined) data.closingDate = b.closingDate ? new Date(String(b.closingDate)) : null;
  await db.job.update({ where: { id }, data });
  return NextResponse.json({ ok: true });
}

// DELETE — delete a job  (unchanged)
export async function DELETE(req: Request) {
  if (!(await verifyAdmin())) return NextResponse.json({ error: "Unauthorized", ok: false }, { status: 401 });
  const url = new URL(req.url);
  const id = url.searchParams.get("id");
  if (!id) return NextResponse.json({ error: "id required", ok: false }, { status: 400 });
  await db.job.delete({ where: { id } });
  return NextResponse.json({ ok: true });
}
```

### Fix 4 — Verify `updatedAt` field on `JobApplication` (Prisma schema)

**Current `JobApplication` model in `prisma/schema.prisma` is missing `updatedAt`:**

```prisma
model JobApplication {
  id          String   @id @default(cuid())
  jobId       String
  fullName    String
  email       String
  phone       String?
  education   String?
  experience  String?
  coverLetter String?
  cvFileName  String?
  cvUrl       String?
  status      String   @default("new")
  createdAt   DateTime @default(now())
  // ← NO updatedAt here
  job         Job      @relation(fields: [jobId], references: [id], onDelete: Cascade)
  ...
}
```

The `PUT` handler in `/api/admin/jobs/applications/route.ts` updates `status`, but without `updatedAt @updatedAt`, there is no way to track when a status was changed. Add it:

**In `prisma/schema.prisma`**, add `updatedAt` to `JobApplication`:

```prisma
model JobApplication {
  id          String   @id @default(cuid())
  jobId       String
  fullName    String
  email       String
  phone       String?
  education   String?
  experience  String?
  coverLetter String?
  cvFileName  String?
  cvUrl       String?
  status      String   @default("new") // new | reviewed | interview | offered | rejected
  notes       String?                   // optional admin notes
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt       // ← ADD THIS
  job         Job      @relation(fields: [jobId], references: [id], onDelete: Cascade)

  @@index([jobId])
  @@index([status])
  @@index([email])
}
```

After editing the schema, run:
```bash
bun run db:push
```
(or `prisma migrate dev --name add-job-application-updatedAt` if you use migrations)
